## EN

> **Note:** LLM-generated summary based on the listed sources; it may be incomplete, outdated or wrong.

### TL;DR

Regression tests check that a system has not become worse after a change. For LLM and RAG systems they matter whenever prompts, retrievers, chunking or models change, because small changes can shift behaviour unpredictably: the same commercial LLM service changed substantially within three months, with GPT-4's accuracy on identifying prime numbers dropping from 84% to 51% (Chen et al., 2023). A regression test does not ask "does the change work?" but "did the change break something that worked before?", including individual cases that a new model gets wrong although the old one got them right (Yan et al., 2020).

### How it works

#### 1. Why classical testing is not enough

Classical software returns the same output for the same input; an LLM system may not. A single passed test case is therefore no proof, and regression tests for LLM systems need a fixed evaluation set and repeatable metrics ([[llm-evaluation|LLM Evaluation]]).

#### 2. Building a regression test set

A test case contains more than a question and an expected answer:

```yaml
id: rt-042
question: "Which notice period applies under contract X?"
expected_answer_contains: "three months"
relevant_sources: ["Contract_X clause 7"]
must_not_contain: ["six months"]
category: contract_analysis
criticality: high
```

The set mixes frequent queries, known edge cases and earlier failures, questions without an answerable basis, and critical cases with high risk. Every error found in the past becomes its own test case, so that it cannot return unnoticed. CheckList helps to generate many test cases along a matrix of linguistic capabilities and test types (Ribeiro et al., 2020).

#### 3. What is checked

- Re-running known test questions against the new version.
- Retrieval results (Recall@k, Precision@k) between old and new configuration ([[rag-retrieval-evaluation|RAG: Retrieval Evaluation]]).
- Answer quality and citations: correctness, faithfulness and citation correctness ([[rag-generation-evaluation|RAG: Generation Evaluation]]).
- Output structure, such as whether required JSON schemas are still met; code generated by GPT-4 and GPT-3.5 had more formatting mistakes in June than in March 2023 (Chen et al., 2023).
- Several metrics beyond accuracy, such as calibration, robustness, fairness, bias, toxicity and efficiency, which make trade-offs visible (Liang et al., 2022).

#### 4. Comparing versions case by case

An aggregate score is not enough. Positive-congruent training calls a sample that the new model gets wrong although the old model got it right a "negative flip" and treats reducing such inconsistencies as being as important in practice as reducing the overall error (Yan et al., 2020). A slightly better average can hide that a critical case solved before now fails.

#### 5. Workflow

```text
change to prompt / model / retriever / chunking
   → run regression test set
   → automated metrics + LLM-as-a-judge
   → no regression: deploy   |   regression: analyse cause, adjust change
```

As in CI/CD pipelines, the regression run is a precondition for deployment, not an optional check afterwards ([[mlops-and-deployment|MLOps and Deployment]]). The ML Test Score likewise lists tests against a simpler baseline, quality checks on important data slices, canary tests before serving and the ability to roll back serving models (Breck et al., 2017).

#### Origin and variants

Regression testing is a core practice of software engineering. For ML, it was extended to data, model quality on important slices and monitoring (Breck et al., 2017), to behavioural test suites (Ribeiro et al., 2020) and to model updates without negative flips (Yan et al., 2020). Drift in hosted LLM services (Chen et al., 2023) made continuous re-testing necessary even without changes on one's own side.

### When to use it

- Before every change to prompt, model, retriever, embedding model or chunking goes live ([[prompt-comparison|Prompt Comparison]]; [[model-comparison|Model Comparison]]).
- Regularly for hosted models, because the provider can change their behaviour without notice (Chen et al., 2023).
- After every fixed bug, to add the case to the set.

### Strengths and limitations

**Strengths**
- Preserves existing quality while the system evolves.
- Makes changes controlled and reproducible to test.
- Finds unwanted side effects early, before they reach production.

**Limitations**
- Only covers what is in the test set; a set that does not grow with new failures loses value.
- Non-deterministic outputs require repeated runs or tolerant checks.
- Automated judges and metrics need calibration against human judgement ([[llm-as-a-judge|LLM-as-a-Judge]]).

### Comparison

| Approach | How it differs | Suited for |
|----------|----------------|------------|
| Regression test | Compares new and old version on a fixed set | Every change before deployment |
| Benchmark evaluation | Broad capability measurement on public tasks (Liang et al., 2022) | Model selection |
| Behavioural test suite | Targeted tests per capability (Ribeiro et al., 2020) | Finding systematic weaknesses |
| Monitoring in production | Watches real traffic after deployment ([[mlops-and-deployment|MLOps and Deployment]]) | Drift and unexpected inputs |

### In practice

Typical rules: a new chunking method may not reduce recall on known test questions; a prompt update may not increase hallucinations or reduce faithfulness; a model change may not break solved critical cases; a new embedding model may not worsen retrieval quality unless this is a deliberate trade-off ([[rag-evaluation|RAG: Evaluation]]; [[retrieval-augmented-generation|Retrieval-Augmented Generation]]). Results per run are stored with the configuration that produced them ([[experiment-tracking|Experiment Tracking]]), and regression testing is part of the wider [[quality-control|Quality Control]], for example for [[legal-ai|Legal AI]] and [[contract-intelligence|Contract Intelligence]].

### Key takeaway

Regression tests run a fixed, growing test set against every new version and compare results case by case, because LLM systems can get worse through small changes on one's own side or through silent updates by the provider.

## DE

> **Hinweis:** LLM-generierte Zusammenfassung auf Grundlage der angegebenen Quellen; sie kann unvollständig, veraltet oder falsch sein.

### TL;DR

Regressionstests prüfen, ob ein System nach einer Änderung nicht schlechter geworden ist. Bei LLM- und RAG-Systemen sind sie wichtig, sobald sich Prompts, Retriever, Chunking oder Modelle ändern, denn kleine Änderungen können das Verhalten unvorhersehbar verschieben: Derselbe kommerzielle LLM-Dienst veränderte sich innerhalb von drei Monaten erheblich, und die Genauigkeit von GPT-4 beim Erkennen von Primzahlen fiel von 84 % auf 51 % (Chen et al., 2023). Ein Regressionstest fragt nicht „Funktioniert die Änderung?", sondern „Hat die Änderung etwas kaputt gemacht, das vorher funktioniert hat?", einschließlich einzelner Fälle, die ein neues Modell falsch löst, obwohl das alte sie richtig gelöst hat (Yan et al., 2020).

### Funktionsweise

#### 1. Warum klassisches Testen nicht reicht

Klassische Software liefert für dieselbe Eingabe dieselbe Ausgabe, ein LLM-System nicht unbedingt. Ein einzelner bestandener Testfall ist daher kein Nachweis, und Regressionstests für LLM-Systeme brauchen ein festes Evaluationsset und wiederholbare Metriken ([[llm-evaluation|LLM-Evaluation]]).

#### 2. Aufbau eines Regressionstest-Sets

Ein Testfall enthält mehr als Frage und erwartete Antwort:

```yaml
id: rt-042
question: "Welche Kündigungsfrist gilt laut Vertrag X?"
expected_answer_contains: "drei Monate"
relevant_sources: ["Vertrag_X Klausel 7"]
must_not_contain: ["sechs Monate"]
category: contract_analysis
criticality: high
```

Das Set mischt häufige Anfragen, bekannte Grenzfälle und frühere Fehler, Fragen ohne beantwortbare Grundlage und kritische Fälle mit hohem Risiko. Jeder in der Vergangenheit gefundene Fehler wird ein eigener Testfall, damit er nicht unbemerkt zurückkehrt. CheckList hilft, entlang einer Matrix aus sprachlichen Fähigkeiten und Testtypen viele Testfälle zu erzeugen (Ribeiro et al., 2020).

#### 3. Was geprüft wird

- Erneuter Lauf bekannter Testfragen gegen die neue Version.
- Retrieval-Ergebnisse (Recall@k, Precision@k) zwischen alter und neuer Konfiguration ([[rag-retrieval-evaluation|RAG: Evaluation des Retrievals]]).
- Antwortqualität und Zitate: Korrektheit, Faithfulness und Zitationskorrektheit ([[rag-generation-evaluation|RAG: Evaluation der Generierung]]).
- Struktur der Ausgabe, etwa ob geforderte JSON-Schemata weiter eingehalten werden; von GPT-4 und GPT-3.5 erzeugter Code hatte im Juni mehr Formatierungsfehler als im März 2023 (Chen et al., 2023).
- Mehrere Metriken neben der Genauigkeit, etwa Kalibrierung, Robustheit, Fairness, Bias, Toxizität und Effizienz, die Zielkonflikte sichtbar machen (Liang et al., 2022).

#### 4. Versionen Fall für Fall vergleichen

Ein aggregierter Score reicht nicht. Positive-Congruent Training nennt ein Beispiel, das das neue Modell falsch löst, obwohl das alte es richtig gelöst hat, einen „Negative Flip" und hält das Verringern solcher Inkonsistenzen in der Praxis für ebenso wichtig wie das Senken des Gesamtfehlers (Yan et al., 2020). Ein leicht besserer Durchschnitt kann verdecken, dass ein zuvor gelöster kritischer Fall jetzt scheitert.

#### 5. Ablauf

```text
Änderung an Prompt / Modell / Retriever / Chunking
   → Regressionstest-Set ausführen
   → automatische Metriken + LLM-as-a-Judge
   → keine Regression: ausrollen   |   Regression: Ursache analysieren, Änderung anpassen
```

Wie in CI/CD-Pipelines ist der Regressionslauf Voraussetzung für das Deployment, keine optionale Nachprüfung ([[mlops-and-deployment|MLOps und Deployment]]). Auch der ML Test Score nennt Tests gegen eine einfachere Baseline, Qualitätsprüfungen auf wichtigen Datenausschnitten, Canary-Tests vor dem Ausrollen und die Möglichkeit, ausgerollte Modelle zurückzurollen (Breck et al., 2017).

#### Ursprung und Varianten

Regressionstests sind eine Kernpraxis der Softwareentwicklung. Für ML wurden sie auf Daten, Modellqualität auf wichtigen Ausschnitten und Monitoring (Breck et al., 2017), auf Verhaltenstest-Suiten (Ribeiro et al., 2020) und auf Modellaktualisierungen ohne Negative Flips (Yan et al., 2020) erweitert. Drift bei gehosteten LLM-Diensten (Chen et al., 2023) macht laufendes erneutes Testen auch ohne eigene Änderungen nötig.

### Wann einsetzen

- Bevor eine Änderung an Prompt, Modell, Retriever, Embedding-Modell oder Chunking live geht ([[prompt-comparison|Prompt-Vergleiche]]; [[model-comparison|Modellvergleiche]]).
- Regelmäßig bei gehosteten Modellen, weil der Anbieter ihr Verhalten ohne Ankündigung ändern kann (Chen et al., 2023).
- Nach jedem behobenen Fehler, um den Fall in das Set aufzunehmen.

### Stärken und Grenzen

**Stärken**
- Erhält die bestehende Qualität, während das System weiterentwickelt wird.
- Macht Änderungen kontrolliert und reproduzierbar testbar.
- Erkennt unerwünschte Nebenwirkungen früh, bevor sie den Betrieb erreichen.

**Einschränkungen**
- Deckt nur ab, was im Testset steht; ein Set, das nicht mit neuen Fehlern wächst, verliert an Wert.
- Nicht deterministische Ausgaben erfordern wiederholte Läufe oder tolerante Prüfungen.
- Automatische Bewertungen und Metriken müssen an menschlichen Urteilen kalibriert werden ([[llm-as-a-judge|LLM-as-a-Judge]]).

### Vergleich

| Ansatz | Unterschiede | Geeignet für |
|----------|----------------|------------|
| Regressionstest | Vergleicht neue und alte Version auf einem festen Set | Jede Änderung vor dem Deployment |
| Benchmark-Evaluation | Breite Messung von Fähigkeiten auf öffentlichen Aufgaben (Liang et al., 2022) | Modellauswahl |
| Verhaltenstest-Suite | Gezielte Tests je Fähigkeit (Ribeiro et al., 2020) | Systematische Schwächen finden |
| Monitoring im Betrieb | Beobachtet realen Verkehr nach dem Deployment ([[mlops-and-deployment|MLOps und Deployment]]) | Drift und unerwartete Eingaben |

### In der Praxis

Typische Regeln: Ein neues Chunking-Verfahren darf den Recall bei bekannten Testfragen nicht senken; ein Prompt-Update darf nicht zu mehr Halluzinationen oder geringerer Faithfulness führen; ein Modellwechsel darf gelöste kritische Fälle nicht brechen; ein neues Embedding-Modell darf die Retrieval-Qualität nicht verschlechtern, außer dies ist ein bewusst eingegangener Zielkonflikt ([[rag-evaluation|RAG: Evaluation]]; [[retrieval-augmented-generation|Retrieval-Augmented Generation]]). Ergebnisse jedes Laufs werden mit der erzeugenden Konfiguration gespeichert ([[experiment-tracking|Experiment Tracking]]), und Regressionstests sind Teil der umfassenderen [[quality-control|Qualitätskontrolle]], etwa für [[legal-ai|Legal AI]] und [[contract-intelligence|Contract Intelligence]].

### Merksatz

Regressionstests lassen ein festes, wachsendes Testset gegen jede neue Version laufen und vergleichen die Ergebnisse Fall für Fall, weil LLM-Systeme durch kleine eigene Änderungen oder stille Updates des Anbieters schlechter werden können.
